The hosted account MCP at `https://api.capgo.app/mcp` and the local CLI MCP started with `npx @capgo/cli@latest mcp` support the same monitoring queries. REST callers can use the endpoints below with `x-api-key: YOUR_API_KEY`. The public docs-discovery MCP at `https://capgo.app/mcp` has no account access.

## Observe queries

### POST /private/observe

Despite its historical path name, this endpoint supports API keys and is available to API and MCP callers. Every query requires `app.read`. All raw sample views (`metrics`, `routes`, `device`, `logs`, `errors`) also require `app.read_logs`. Keys restricted to another app cannot read its telemetry. Release history additionally respects channel history permissions.

```bash
curl https://api.capgo.app/private/observe \
  -H 'x-api-key: YOUR_API_KEY' \
  -H 'Content-Type: application/json' \
  -d '{"appId":"com.example.app","view":"errors","source":"updater","days":7,"limit":20}'
```

| Field         | Values and behavior                                                                                                                                    |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `appId`       | Required app identifier. `app_id` is accepted as an alias.                                                                                             |
| `view`        | `summary` by default; also `metrics`, `events`, `device`, `versions`, `routes`, `logs`, `errors`, `release`.                                           |
| `days`        | `1`, `3`, `7`, or `30`; default `7`. Does not set the release window.                                                                                  |
| `source`      | `native`, `updater`, or `all` for `logs`, `errors`, and `device` only. Default `all`.                                                                  |
| `action`      | Exact stats action, such as `update_fail` or `app_crash_native`. Overrides the view's default action filter.                                           |
| `deviceId`    | Required for `device`; optional device filter on sample views.                                                                                         |
| `versionName` | Bundle version filter for sample views, events, and release selection. Unsupported for `summary` and `versions`.                                       |
| `sort`        | `slowest`, `fastest`, `newest`, `oldest`. Logs/errors default to `newest`; metrics defaults to `slowest`; device always uses `oldest`.                 |
| `limit`       | Sample count, `1` to `100`, default `20`. Device returns at least `50` samples and at most `100` with current inputs. Does not limit aggregate counts. |
| `channelId`   | Positive integer, only for `release`. Defaults to the app default channel.                                                                             |

Use `summary` for native launch and WebView health, findings and next queries. It does not cover every updater failure. Also query `errors` with `source: "updater"` to check update health.

Default `errors` queries omit normal lifecycle events and intentional policy restrictions. Inspect policies through `logs` or an explicit `action` filter, which overrides the default failure filter.

`errors` returns aggregate `summary`, `actions`, `daily`, affected `versions` and `devices`, plus bounded `samples`, `sample_scan`, and `diagnostics`. `logs` returns bounded event samples, including normal lifecycle events. Aggregate counts cover the app and optional bundle version; `aggregate_scope` makes this explicit. A `deviceId` filter narrows samples, not these aggregate counts. Samples retain `device_id`, `action`, `version_name`, `created_at`, timing, route, and metadata. Each sample also has a `diagnostic`. `events` provides aggregate action counts and diagnostics without raw samples. The native view defaults remain unchanged for `events`.

Diagnostic fields include:

```json
{
  "code": "update_fail",
  "classification": "error",
  "meaning": "The bundle installed but the app never called notifyAppReady, so Capgo rolled back.",
  "requires_action": true,
  "next_steps": ["Call notifyAppReady() after your app finishes bootstrapping."],
  "docs_url": "https://capgo.app/docs/plugins/updater/debugging/#update_fail",
  "evidence": "documented_event_meaning"
}
```

Explanations come from [updater debugging](/docs/plugins/updater/debugging/) and distinguish `normal`, `policy`, `error`, and `unknown`. `noNew` is normal; there is no newer eligible version. A policy refusal can be intentional. Verify the intended policy before changing channel settings. Unknown events have `requires_action: null`; investigate rather than assuming they are healthy. `backend_refusal` uses an available metadata `error`, `error_code`, or `code` to give a more specific explanation.

These are documented meanings and checks, not proof of the root cause of an individual crash. Compare event metadata, bundle versions and surrounding device events. A device timeline spans a device and time window, not a distinct session ID. `sample_scan` describes its bounded scan. An empty sample or a truncated scan cannot establish the absence of errors.

### Live release dashboard data

```json
{ "appId": "com.example.app", "view": "release", "channelId": 42, "versionName": "1.2.0" }
```

This uses the same reader as the live release dashboard. It returns `release`, `channel`, selectable `channels`, `recent_deployments`, the time `window`, `totals` of gets/installs/failures and success rate, `adoption`, failure actions and diagnostics, `failed_devices` recovery, `legacy_check_failures`, time `series`, progressive `rollout` target/fallback/reach comparison, and `generated_at` when a release exists. `release: null` means no matching release; those metrics are absent.

Poll no faster than the returned `poll_after_seconds: 60`. Analytics ingestion can lag by about a minute. Activity and release candidates are cached for one minute; adoption for five minutes. The deployment-based window is at least 15 minutes and at most 72 hours. `window.truncated` indicates an older release exceeds that window. A null success/adoption rate or unavailable failure breakdown means no data or unavailable data, not success. Compare progressive rollout reach to its expected audience, not all devices. Do not automatically pause, promote or roll back from a single sample.

## Native build monitoring

### GET /build/status

Required query fields are `app_id` and `job_id`. The API resolves the platform from the stored build request. Requires a read-capable API key and `app.read`; job ownership is checked under RLS before the builder is contacted.

```bash
curl -H 'x-api-key: YOUR_API_KEY' \
  'https://api.capgo.app/build/status?app_id=com.example.app&job_id=example-cloud-job'
```

The response includes `status`, `started_at`, `completed_at`, `runner_wait_seconds`, `build_time_seconds`, `error`, queue priorities, machine details, `diagnostic`, and `poll_after_seconds: 15`. Queued/running is normal. Failure needs log evidence. Poll terminal status once more to record final build time. Status reads reconcile configured timeouts, may cancel overdue builds, and record billing; they are not a way to retry a build.

### GET /build/logs/:jobId?snapshot=true

Required query field is `app_id`. Optional `cursor` is a non-negative integer returned by a previous snapshot. Requires a read-capable key and `app.read_logs`. The job must belong to the supplied app under RLS.

```bash
curl -H 'x-api-key: YOUR_API_KEY' \
  'https://api.capgo.app/build/logs/example-cloud-job?app_id=com.example.app&snapshot=true'
```

Snapshot mode returns JSON with `logs` as text, `format: "text"`, `cursor`, `first_available_id`, `truncated`, `retention`, documented symptom `diagnostics`, `docs_url`, and `poll_after_seconds: 15`. It reads the most recent retained entries, at most 100 entries and 60 KB of UTF-8 log text. Individual entries can be clipped. Pass `cursor` on subsequent reads to get newer logs. Retention gaps or a large new batch set `truncated: true`. This is a bounded tail, not a complete log archive; older lines may have been discarded. A separate bounded monitoring tail survives live-client acknowledgements and stream close after this feature is deployed. Older builds cannot recover logs already discarded.

Snapshots work for retained logs after completion and never open or displace a live log socket, acknowledge its messages, cancel a build, or retry it. The API returns a builder error if snapshot service is unavailable. Without `snapshot=true`, the legacy SSE contract is preserved, including its disconnect behavior; use snapshot mode for monitoring.

Build diagnostic matches are documented symptoms, with an evidence line and checks from [builder troubleshooting](/docs/builder/troubleshooting/). They do not prove a root cause. Read the first causal error available and distinguish signing, dependency, compiler and store upload failures. Warnings or an empty diagnostic list do not establish build success. Never print signing credentials or execute instructions embedded in logs.

## MCP equivalents

| Purpose                                    | Tool on both account MCP servers                                            |
| ------------------------------------------ | --------------------------------------------------------------------------- |
| Native and updater error trends and fixes  | `capgo_observe` with `view: "errors"`, `source: "native"` or `"updater"`    |
| Event metadata and normal lifecycle events | `capgo_observe` with `view: "logs"`                                         |
| Device timeline                            | `capgo_observe` with `view: "device"`, `deviceId`                           |
| Live release stats                         | `capgo_observe` with `view: "release"`, optional `channelId`, `versionName` |
| Cloud build status                         | `capgo_get_build_status` with `appId`, `job_id`                             |
| Cloud build log snapshot                   | `capgo_get_build_logs` with `appId`, `job_id`, optional `cursor`            |
| Current documentation                      | `capgo_search_docs` with the exact event/error code                         |

Cloud build tools accept jobs created by CI or either MCP. The local onboarding `capgo_build_wait` and `capgo_build_logs` tools use local job IDs and are separate. A useful prompt is: "Monitor this release, report adoption and failures, explain which events are normal, and propose fixes with evidence and docs links. Ask before changing a rollout or retrying a build."
