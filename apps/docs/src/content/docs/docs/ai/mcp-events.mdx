MCP Events let an agent **subscribe** to specific Capgo activity and receive **signed webhook deliveries** on an HTTPS URL you provide. The agent does not need to poll build status, bundle uploads, or channel deployments.

Capgo models this on the [draft MCP Events specification](https://modelcontextprotocol.io) in the same spirit as other hosted MCP providers (for example Vercel). Deliveries use [Standard Webhooks](https://www.standardwebhooks.com/) signing. The hosted account MCP server at `https://api.capgo.app/mcp` exposes both protocol methods and `capgo_*` tool wrappers for clients that do not speak the Events protocol yet.

<Aside type="note" title="Hosted only">
  MCP Events exist on the **hosted** account MCP server. The [local CLI MCP server](/docs/cli/reference/mcp/) runs over stdio and cannot receive inbound webhooks, so it does not offer event subscriptions.
</Aside>

<Aside type="caution" title="No delivery guarantees">
  Webhooks are best-effort. Capgo does not guarantee ordering, exactly-once delivery, or a maximum latency. Treat each delivery as a signal to refresh state or run a follow-up tool call. Failed deliveries are not replayed in v1.
</Aside>

## How it works

1. Your MCP client calls `events/subscribe` (or `capgo_subscribe_events`) with an HTTPS callback URL, the event name, and filter arguments.
2. Capgo runs the usual [HTTPS webhook verification challenge](/docs/public-api/) on that URL before the first event.
3. When matching activity happens in your organization, Capgo `POST`s a JSON envelope to your URL with Standard Webhooks headers.
4. Calling `events/subscribe` again for the same subscription **refreshes** its time to live (TTL). When TTL expires, deliveries stop until you subscribe again.

On `initialize`, the server advertises `capabilities.events` so clients know Events are available.

## Event catalog

| Event name | When it fires |
| ---------- | ------------- |
| `build.succeeded` | A cloud native build reaches a successful terminal state. |
| `build.failed` | A cloud native build fails or times out. `data.failure_category` is `timeout` when the job hit the build timeout. |
| `bundle.uploaded` | A new app bundle version row is created from a real upload (not a metadata-only change). |
| `bundle.deployed` | A channel's assigned bundle version **changes** (a deployment). Metadata-only channel updates do not emit this event. |

Every payload includes `org_id` and `app_id` inside `data`. Build events add build fields; bundle events add bundle or channel fields.

### Subscribe filters (`arguments`)

| Argument | Required | Applies to | Meaning |
| -------- | -------- | ---------- | ------- |
| `org_id` | Yes | All events | Organization to watch. |
| `app_id` | No | All events | Limit deliveries to one app. Omit to receive events for any app in the org you can read. |
| `channel` | No | `bundle.deployed` only | Limit deployments to one channel name. |

## Protocol methods and tools

### MCP protocol (JSON-RPC)

| Method | Purpose |
| ------ | ------- |
| `events/list` | List event types and their argument schema (catalog). |
| `events/subscribe` | Create or refresh a subscription. Same call extends TTL when the subscription already exists. |
| `events/unsubscribe` | Remove a subscription and stop deliveries. |

### Account MCP tools

These wrap the same behavior for clients that only support tools today:

| Tool | Purpose |
| ---- | ------- |
| `capgo_list_event_types` | Same information as `events/list`. |
| `capgo_subscribe_events` | Subscribe or refresh. Can generate a `whsec_` signing secret when you do not pass one; the secret is returned **once** in the tool result. |
| `capgo_list_event_subscriptions` | List active MCP event subscriptions for the org. |
| `capgo_unsubscribe_events` | Remove a subscription by id. |

On the **protocol** subscribe path, you must supply the webhook signing secret. Capgo never echoes that secret back on later calls.

Existing console webhook tools (`capgo_list_webhooks`, `capgo_create_webhook`, and so on) are unchanged. MCP event subscriptions are stored as webhook rows with `source: mcp` and appear in the console webhooks list with an **MCP** badge. Org admins can delete them there.

## Delivery envelope

Each `POST` body is a single JSON object:

```json
{
  "eventId": "01J8Z...",
  "name": "build.succeeded",
  "timestamp": "2026-11-10T12:00:00.000Z",
  "cursor": null,
  "data": {}
}
```

`cursor` is reserved for future pagination and is always `null` in v1.

### Example: `build.succeeded`

```json

  "eventId": "01J8ZXAMPLEBUILDOK",
  "name": "build.succeeded",
  "timestamp": "2026-11-10T12:00:00.000Z",
```

## HTTP headers and signature verification

Capgo sends Standard Webhooks headers on every delivery:

| Header | Role |
| ------ | ---- |
| `webhook-id` | Same value as `eventId` in the body. |
| `webhook-timestamp` | Unix timestamp (seconds) when the message was signed. |
| `webhook-signature` | One or more signatures, each `v1,<base64>` HMAC-SHA256 over ``${webhook-id}.${webhook-timestamp}.${rawBody}`` using the subscription secret (without the `whsec_` prefix). |
| `X-MCP-Subscription-Id` | Capgo subscription id for debugging and `events/unsubscribe`. |

MCP event deliveries do **not** use the legacy `X-Capgo-Signature` header.

Reject requests when the timestamp is too far from your server clock (for example more than five minutes). Always verify against the **raw** request body bytes, not a re-serialized JSON object.

### Node.js verification sketch

```ts
import { createHmac, timingSafeEqual } from 'node:crypto'

function verifyStandardWebhook(
  rawBody: string,
  webhookId: string,
  webhookTimestamp: string,
  webhookSignatureHeader: string,
  secretWithPrefix: string,
): boolean {
  const secretBase64 = secretWithPrefix.startsWith('whsec_')
    ? secretWithPrefix.slice('whsec_'.length)
    : secretWithPrefix
  const secretKey = Buffer.from(secretBase64, 'base64')

  const signedContent = `${webhookId}.${webhookTimestamp}.${rawBody}`
  const expected = createHmac('sha256', secretKey).update(signedContent, 'utf8').digest('base64')

  for (const part of webhookSignatureHeader.split(' ')) {
    const [version, sig] = part.split(',', 2)
    if (version !== 'v1' || !sig) continue
    const a = Buffer.from(sig)
    const b = Buffer.from(expected)
    if (a.length === b.length && timingSafeEqual(a, b)) return true
  }
  return false
}
```

## Subscription lifetime and limits

| Topic | Behavior |
| ----- | -------- |
| Default TTL | **24 hours** from subscribe or refresh. |
| Refresh | Call `events/subscribe` (or `capgo_subscribe_events`) again with the same URL, event, and arguments before expiry. |
| Unlimited TTL | Not supported. |
| Callback URL | **HTTPS only.** Same SSRF and safety checks as console webhooks. |
| Verification | URL must pass the verification challenge before the first event is sent. |
| Active subscriptions per org | **25** maximum. |
| Permissions | Requires `org.update_settings` (org settings admin), the same right as managing organization webhooks today. **App-scoped API keys cannot subscribe.** The key must be allowed to read every app matched by your filters. OAuth-connected MCP sessions follow the delegated key RBAC. |

## Typical agent workflow

```text
events/list or capgo_list_event_types
  -> pick build.succeeded / build.failed / bundle.*
capgo_subscribe_events({ url, name, arguments, secret? })
  -> save subscription id and whsec_ secret
on POST: verify Standard Webhooks headers
  -> capgo_get_build_status / capgo_observe / channel tools as needed
before TTL: capgo_subscribe_events again to refresh
capgo_unsubscribe_events when done
```
