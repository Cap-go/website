# Website Apple account creation

This website change depends on the shared backend/iOS Apple authentication PR on `Cap-go/capgo.app` (`wolny/shared-apple-auth`, authoritative `docs/apple-auth-api.md`). Deploy that PR's database migration, API and console before enabling this website option. Merging the website PR alone leaves Apple hidden.

Email remains the first action on `/register/`, including translated routes. Apple appears below it only when `GET https://api.capgo.app/auth/apple/capabilities` returns `web.enabled: true` and includes the exact `https://console.capgo.app/login` callback in `web.redirect_uris`. Failed, malformed, disabled or missing capabilities leave email available. Availability is checked again on click.

The website opens `https://console.capgo.app/login?apple_oauth=1` in a popup. Only allowlisted attribution, device and experiment tags, plus a random website correlation state, enter that URL. The console owns PKCE/state, `/auth/apple/start`, Apple's server callback, `/auth/apple/exchange`, session installation, MFA and onboarding. The website never exchanges Apple credentials or transfers a session. A blocked popup falls back to the same console flow in the current tab.

After exchange, the console sends a completion receipt to the website. The website checks the exact console origin, retained popup reference and retained state, and accepts one receipt. `user_signed_up`, OpenAI `registration_completed`, Datafast `signup` and affiliate signup run only for the backend's `is_new_user: true`, with the website's original attribution and experiment. Returning accounts and cancelled/failed attempts do not count as signups. Names are optional and are not included in this receipt. Closing the popup restores both registration actions. A same-tab fallback signs in but cannot send a website popup conversion receipt.

## Operator setup and rollout

1. Deploy the shared backend migration/API and console completion handler first. Keep `WEB_APPLE_LOGIN_ENABLED` false while configuring and testing. No provider settings or flags are changed by this website PR.
2. In Apple Developer, enable Sign in with Apple on the native primary App ID. Register a web Services ID, associate it with that primary App ID, and register the approved website domains/subdomains and the exact HTTPS API callback, `https://api.capgo.app/auth/apple/callback`. The website's entry page is `https://capgo.app/register/`; the consumer completion URL is `https://console.capgo.app/login` (no trailing slash). The Apple callback goes to the shared API.
3. Configure the backend's server-only `APPLE_SIGN_IN_CLIENT_ID`, `APPLE_SIGN_IN_TEAM_ID`, `APPLE_SIGN_IN_KEY_ID`, `APPLE_SIGN_IN_PRIVATE_KEY`, `APPLE_SIGN_IN_WEB_CLIENT_ID` and `APPLE_SIGN_IN_OAUTH_CALLBACK_URL`. Set `APPLE_SIGN_IN_REDIRECT_URLS` to an exact allowlist containing `"https://console.capgo.app/login"` plus any separately approved native app callbacks. Never put signing secrets in website environment variables or use wildcard redirects.
4. Enable the Supabase Apple provider for the native audience and web Services ID according to the backend contract. Preserve normal account linking, enforced SSO, CAPTCHA and disabled/deleted-account rules. Configure Apple's private email relay for Capgo's sending domains so relay users can receive account mail.
5. Run credentialed smoke tests for a first authorization (including Apple's one-time `user.name`), a returning/linked account, Hide My Email, a missing name, cancellation, CAPTCHA, enforced SSO, account status and MFA. Confirm the backend persists the first name before interrupted client completion and never erases chosen names on later sign-ins. The console permits normal profile editing when Apple has no name.
6. Only after those checks, explicitly enable the backend `WEB_APPLE_LOGIN_ENABLED` rollout setting. Verify the capabilities response and the complete website → console → Apple → console flow. Disable that setting to hide the option again. The browser checks cannot prove Apple Portal audience/return-URL configuration by themselves.

Production completion receipts target only `https://capgo.app`. Preview/local environments require separately reviewed origin and redirect configuration; do not loosen origin checks to suffix matching. For an ongoing branch A/B experiment, apply the website entry change to every active branch before enabling Apple, so each variant has the same account-creation options.

## Verification

`bun test apps/web/test/apple-signup.test.ts` checks availability, URL metadata, trusted receipt validation and new-user-only conversion events. After building, `bun test scripts/tests/apple-signup.browser.test.ts` exercises the built page in Chromium with isolated capability/console fixtures for new and returning users, cancellation, revoked availability, blocked popups and the existing email request. These tests do not authorize against Apple or prove deployed provider configuration. The PR includes desktop/mobile visual comparison of `/register/` with an enabled capability fixture.

References: [Apple web configuration](https://developer.apple.com/help/account/capabilities/configure-sign-in-with-apple-for-the-web/), [Apple authorization response](https://developer.apple.com/documentation/signinwithapplerestapi/request-an-authorization-to-the-sign-in-with-apple-server), [Supabase Apple documentation](https://supabase.com/docs/guides/auth/social-login/auth-apple). Apple's name is supplied separately on initial authorization; the shared backend owns that persistence, rather than a website Supabase OAuth fallback.
